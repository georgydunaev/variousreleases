The Problem: Modern Proof Assistants

  • Too complex for ordinary mathematicians (Lean, Coq, Isabelle)
  • Rely on computational tricks that hide the logic (tactics, SMT, unification)
  • No independent, portable certificates
  • Hard to adapt for verifying executable specifications (smart contracts)

Our goal – a proof assistant that combines mathematical clarity, reliability, and practical applicability.

2

Existing Project: CakeML

  • Only parametric polymorphism (types depend on types)
  • Missing full polymorphism (types depend on values)
  • Obelisk’s solution: add one abstraction layer + code generation → expressive power without sacrificing simplicity

What Is Obelisk?

Website: https://ObeliskProofAssistant.github.io/

A proof assistant built on these principles:

  • Zero implicit computation – no reduction or normalisation magic in the kernel. Every proof step is an explicit syntactic tree, checkable by hand.
  • Pure declarative syntax – like a mathematical paper, not a functional program. No tactic noise (intro, apply, rewrite) – low learning curve.
  • Ultra‑small trusted kernel (~20k LOC) – no heavy type‑theory engine; the kernel can be manually audited.
  • Stable definitions – proofs do not break when definitions change, because nothing is computed during verification. AI‑friendly and reusable.
  • Clear error messages – no “failed to synthesise instance” nightmares. Errors point directly to missing logical premises.

Logical Foundations of Obelisk (Overview)

Core logic is based on class theory (similar to NBG). Key definitions:

  • “Set” – a class that is an element of another class.
  • “Proper class” – a class that is not a set.
  • Empty set, universal class, subclass – standard definitions.
  • Extensionality, heredity, exponent (power class), regularity – axioms ensuring set‑theoretic properties.
  • Transitivity and ordinality – defined classically; the class of all ordinals On is itself an ordinal class.

All proofs are built explicitly, without computation – the foundation of reliability.

Comparison: Lean

  • Lean is difficult for mathematicians (dependent types, tactics, complex unifier).
  • Obelisk gives a direct, explicit style close to paper mathematics.

6

Comparison: Metamath

  • Metamath “glues” unrelated statements, lacks reflection and polymorphism.
  • Obelisk supports full polymorphism and abstraction.

7

Comparison: HOL4 (CakeML)

  • Limited expressiveness (only parametric polymorphism).
  • Obelisk solves this via abstraction + code generation.

8

Comparison: Coq

  • Coq focuses on low‑level software verification automation – a different niche.
  • Obelisk targets mathematical clarity and verification of specifications (e.g., smart contracts).

9

Comparison: Isabelle

  • Many abstraction layers, complex to understand.
  • Obelisk has a minimal, transparent kernel.

10

Comparison: Mizar

  • Mizar is built for mathematical literature, but its implementation is monolithic and hard to extend.
  • Obelisk has a modern modular kernel and supports executable code generation.

11

Comparison: Idris / Agda

  • Idris verifies by normalisation (computation) – leads to computational opacity.
  • Obelisk proves equalities step‑by‑step – no need to trust an evaluator.
  • Idris is a programming language with effects (IO); its logic is unsound due to partiality.
  • Obelisk is total and logically consistent.
  • Idris proof terms disappear after compilation; Obelisk exports portable, human‑readable proof certificates.

12

Comparison: HOL Light / ACL2 / PVS

  • Heavy reliance on tactics (rewriting, SMT) – proof scripts are unreadable and brittle.
  • Obelisk proofs are static lists of logical steps – readable even by auditors.
  • No dependence on external SAT/SMT solvers – the kernel is self‑contained.
  • Optimised for explanatory power, not speed – essential for regulated industries (finance, aerospace) where auditors must understand why a property holds.

Why Not Haskell?

  • Haskell is a programming language, not a proof assistant.
  • Logically inconsistent – general recursion, undefined, error introduce ⊥ :: a.
  • Unreliable GHC backend – a property verified today may break with the next compiler update.
  • No independent proof object – type‑checks are lost after compilation.

How Obelisk beats Haskell:

  • Totality – every function is guaranteed to terminate.
  • Certified proofs – explicit, portable certificate re‑checkable by a tiny verifier.
  • Mathematical consistency – built on solid foundations (class theory / HOL).

Conclusion

Obelisk is the anti‑“vibecoding” for proofs:

  • Transparency over magic
  • Explicitness over implicit computation
  • Reliability over trust in huge systems

Mission – make formal verification accessible to mathematicians, engineers, and auditors, while remaining suitable for real‑world executable specifications (smart contracts, critical software).
